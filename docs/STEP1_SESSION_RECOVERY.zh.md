# 静态模拟会话的完整事件恢复

实现：`multigroup/session_recovery.py`、`session_artifacts.py`及`StaticDeploymentSession.restore`。
恢复契约使用journal schema 3；早期schema 1／2工件保留原样，不能用当前恢复器假装升级。
输入观测契约仍为`udc.step1.static_global.v1`。

## 事件提交

每次调用在规划和运动之前保存frame、observation和intent，并创建唯一事件目录。
intent绑定事件编号、前一receipt及session头哈希。只有完整metrics、planning、state、trajectory和checkpoint全部保存，
才写最终receipt作为提交标记。事件和文件拒绝覆盖。
session头另有独立receipt。JSON明确写LF字节，哈希对应实际文件字节，不受Windows换行转换影响。

checkpoint保存实际Guide终态、仿真时钟、已交付布局／群标签、稳定人员ID、冻结半径／需求、分群、已消费frame_id和halted状态。
它绑定前一事件receipt和session头；源码树及Python／数值依赖版本在头中冻结。
每次规划前检查当前日志头和源码／环境，恢复时校验所有完整事件及链。

## 写者与恢复

系统文件锁只允许一个写者；进程退出后由OS释放锁，不能把旧锁文件的存在当作活跃进程证据。
同一对象也拒绝并发step与执行中close，已关闭对象不能继续发出运动。

恢复必须同时满足：

- 当前源码／环境与日志绑定一致；完整事件、checkpoint和头哈希一致；
- 调用方提供的实际机器人反馈逐位匹配已提交物理终态；
- 反馈属于相同逻辑仿真时钟，不推断未知时间间隔内没有运动；
- 没有未提交事件、缺失receipt、断链、事件间物理重置或时钟倒退。

恢复会保留科学失败后的halted状态，不自动重试失败任务。
若运动中退出，pre-motion intent会留下未提交事件，即使旧机器人坐标恰好匹配，也拒绝原地续跑。
半写工件原样保留；后续实际状态接管需要另立协议，不能补写一条虚构轨迹。

## 已测范围和限制

已检验：完成事件后的进程直接退出、OS释放写锁、下一输入的决策与实际轨迹逐位复现、实际状态／时钟不符拒绝、
日志改写拒绝、源码漂移拒绝、科学halt保留、并发命令拒绝，以及执行中退出留下intent并拒绝续跑。
手写恢复开发v2含4个实际事件，两次会话各2次交付，独立物理／会计审计一致，完整任务成功0；
另保留4项预定恢复拒绝见证，不作为新独立样本。

这是完整事件边界、相同仿真epoch下的恢复能力，不是任意掉电的fsync保证，也不是实时机器人backend的无缝接管。
未知时间段／半写事件下的物理运动与服务不能记作零违反或已完成。
