# Step 2a 协议：两个静态群体

状态：确定性开发执行已接入，科研实验仍关闭。`experiments_open: false`，`run_in_this_round: false`。开发执行只从显式入口读取已通过的预检目录。资源分配通过、规划预检通过和完整部署成功仍然分开。一个手写案例的 `SUCCESS` 只说明该案例，不说明 Step 2a 的泛化或方法优势。

Step 1 的单群 `prepare`、部署、导航、安全和独立验收保持原样。动态移动、扩散、分裂、合并、crowd–guide 动力学交互，以及跨群调配的执行，都不在本轮。

## 目标

两个静态群体、固定总人数、固定共享 Guide 预算、精确全局观测、无限通信、无 crowd–guide 动力学交互。

人员位置在初始化后冻结。控制器仍然只消费全体人员的 `Observation(positions, radii, demand)`、Guide 位置和已知场地。生成多边形不进入边界估计，也不进入分配器。需求仍是数值权重，不是风险，也不是 Guide 台数下界。

## 身份和几何

`Observation` 没有人员 ID。稳定身份在冻结的 `PedestrianState.ids`：第 `k` 行的身份是 `int(ids[k])`，对应同一行的位置、半径和需求。`Perception.observation()` 会丢掉这些 ID。

成员 ID 是这些稳定身份，不是观测数组下标。规划预检从冻结 ID 建立行号映射。分配器本身仍不接收 `Observation`，也不读取出生多边形。

完整划分由编排在调用分配器之前执行 `validate_member_partition`：两群成员不相交，并集恰好等于冻结人员 ID。分配器只检查自己收到的两群内部没有重复或重叠成员；它看不到全体人员，因此不能代替这道检查。

几何仍由后续编排按行号映射去读冻结观测。本轮分配器不调用部署规划器。

## 下界政策

下界政策决定每群最少几台 Guide，并在分配前写死。它不是分配策略，也不能当作竞争基线。公平比较必须共享同一种下界政策和同一组整数下界。更换下界来源是资源条件变化，不是方法收益。一次分配里的两群必须使用同一种政策。

- `declared`：调用者直接给出非负整数。记录里没有曲线长度。
- `curve_ceil`：下界是 `ceil(L / H_p)`。记录同时保存该群曲线长度 `L` 和规划间隙 `H_p`。整数必须等于用这两个保存值算出的 `ceil`。原先写的 `independent_ceil` 就是这条下界政策，不再作为第三种分配基线。

下界单位是 Guide 台数。它不是需求权重之和。

## 分配策略

策略只决定已经给定的 Guide ID 如何对应到两个群体。通过只说明共享身份集合满足所给下界。它不说明目标几何、路径、联合安全或 40 秒执行可行。

已实现：

- `floor_then_size`
- `frozen_initial_split`

`independent_ceil` 作为策略名会拒绝，并且不会自动改跑 `floor_then_size`。其他未列出的策略同样拒绝。

输入顺序不影响结果。群体和 Guide 都按身份排序，不按请求里的出现顺序。

### floor_then_size

设两群成员数为 \(n_g\)，总和为 \(N\)，下界为 \(f_g\)，Guide 数为 \(B\)。

若 \(\sum f_g > B\)，返回 `BUDGET_SHORTFALL`：`feasible=false`，分配为空。不给出部分分配，不降低下界，不重抽人员。

否则剩余 \(R=B-\sum f_g\)。每群先得 \(f_g\)，再得 \(\lfloor R n_g / N \rfloor\)。还没分完的席位一次一个，先给 \(n_g\) 更大的群；人数相同则给 `group_id` 字典序较小的群。两个群体时，这个余数是 0 或 1。

台数确定之后，按 `group_id` 字典序取 Guide：每群依次拿走当前剩余 ID 中最小的若干个。输出再按 Guide ID 排序。因此同一组身份重复调用，结果相同。

### frozen_initial_split

映射由调用者显式给出，类型是 `(guide_id, group_id)` 对的序列，不能是会吞掉重复键的字典。

结构不合法时抛出输入错误，不记成科学失败：

- 缺一台 Guide，或没有覆盖全部 Guide：`MAPPING_INCOMPLETE`
- 同一 Guide 出现两次：`DUPLICATE_GUIDE`
- Guide 不在共享预算里：`UNKNOWN_GUIDE`
- 群体不在这两个群里：`UNKNOWN_GROUP`

结构合法之后才看资源：

- 下界之和大于 Guide 数：`BUDGET_SHORTFALL`。这时任何映射都不可能同时满足两群下界。
- 下界之和不超过 Guide 数，但这份固定映射使某一群低于自己的下界：`FROZEN_FLOOR_VIOLATION`。预算本身够，失败的是这份固定映射。分配仍为空，不把违约映射当成已安装结果。
- 每个群都不低于下界：`feasible=true`，分配就是这份映射。

## 输入错误

类型错误、重复群体、空群、成员重复或重叠、下界缺失、重复或为负、下界追溯与 `ceil(L/H_p)` 不一致、两种下界政策混用，都抛出 `AllocationInputError`。它们不是 `BUDGET_SHORTFALL`，也不进入科学失败分母；调用方还没有形成一个合法的实验行。

## 结果含义

`feasible=true` 只表示每个 Guide ID 恰好出现一次，身份集合与输入相同，并且每群台数不少于下界。

它不表示曲线可以生成、目标进入导航域、路径存在、区间安全，或 40 秒内到达保持。群级验收和系统级验收仍是以后的执行阶段。一行实验 `SUCCESS` 必须两级都通过。预算不足、固定映射违约、任一群的几何或规划拒绝、超时、恢复耗尽、路径不可达、安全违反、群级通过但系统级失败，以及程序错误，都留在完整分母里。

本轮只有一次性静态分配。跨群调配的执行、代价和全局安全整合尚未实现。分配器不写出调配事件。

## 与 Step 1 接口的关系

`ResourceAllocator.allocate(groups, guide_count)` 保持不变，Step 1 不调用它，也不调用 `udc.allocation`。新的入口是 `udc.allocation.allocate`。

## 全局安全与两级验收

开发执行政策 `fixed_paths_no_recovery_v1` 使用这些阈值，但不调用 Step 1 的恢复。它不等价于原三次恢复预算。配置在 `configs/step2a/fixed_paths_no_recovery_v1.yaml`。

安全过滤仍是全局的。一台 Guide 与所有人员、所有其他 Guide 和墙的中心距都要检查。

群级验收：该群获配的 Guide 覆盖该群成员所对应的部署目标，并满足与 Step 1 相同的弧间隙、贴线和到达保持。系统级验收：两群都通过，全局安全通过，Guide 身份构成一个划分，共享预算没有超配。

不放宽 Step 1 的安全、覆盖、截止或到达阈值。

## 规划预检

接线基线固定为现有凸包 `estimate_boundary` 和 Equal Arc，相位只有 `0`。这不是方法比较，也不是 256 相位搜索。参数写在 `WIRING_BASELINE`：外偏移 1.3 m，采样 0.1 m，墙距和人群缓冲 0.55 m，规划间隙 \(H_p=1.94\) m，Guide 间距 0.75 m。

数据流是：冻结人员与 Guide → `PedestrianState` 式的 ID 到行号映射 → 完整成员划分 → 各群自己的位置、半径和需求 → 凸包曲线 → `curve_ceil` 或声明下界 → 已有纯分配 → 每群目标数等于获配数量 → 两群占据并集上的共同静态域 → 全体目标的入域和间距 → 只在同群内匹配路径。

共同域先保留每群占据多边形，再做 `unary_union`。不用两群的共同凸包。随后的物理膨胀、`simplify(0.10)` 和 `buffer(0.11)` 仍是现有 `navigation_domain`。可见图对单个多边形仍只取原来的外环；多个多边形时每个分量都进入节点，不选最大分量。

`navigate_and_assign` 的全局匹配可能把 Guide 派到另一群目标，预检不调用它。`assign_within_groups` 只在同一 `group_id` 内匹配。路径的起点检查仍看到全部 Guide。每段路径用共同域上的完整线段检查。这只说明静态路径和指派合格，不证明同时运动时没有碰撞。

成功状态是 `PREFLIGHT_ACCEPTED`。到达、保持、动态区间安全和实际路程保持未评价，不记成 0，也不写运动轨迹。工件用 `preflight.json`，不写 Step 1 的 `metrics.json`。因此现有执行汇总不会把它算进成功率或成功耗时。

几何失败不伪造下界，也不继续分配。预算不足和固定映射违约在规划之前停止。声明下界即使分配通过，仍要接受数量证书和弧间隙检查；失败时不增补 Guide。清单登记之后的意外异常记为 `EXPERIMENT_ERROR`，保留已写出的工件。

离线复判只重算身份、下界分配、共同域、目标间距和路径线段，不重新规划，不改 `preflight.json`。

## 开发执行

`fixed_paths_no_recovery_v1` 只读取已经复判合格的预检目录，输出到新目录。人员、归属、目标和路径都来自该工件。不重新规划，不重新匹配，不增减 Guide，不改变群体归属。`recovery_policy=disabled`，不调用会做全局重指派的 `recover`。截止仍是 40 秒，安全、速度、到达、贴线、间隙和保持阈值与 Step 1 相同。持续停滞记为 `STALL`，并写明没有调用恢复；这不是 `REPLAN_EXHAUSTED`。

每个时间步先沿固定路径得到全体名义速度，再对全部 Guide 调用一次现有联合安全过滤。过滤后的候选还要重查全体区间安全和共同域上的完整线段。通过之后才同时推进。两群不能分别过滤再拼接。初态违规直接拒绝，不包装成零速 fallback。候选被拒绝和已经执行的安全违反分开记录。

验收只读保存的轨迹。群级检查各自的几何、身份、到达、速度、贴线和弧间隙。系统级检查全体身份、区间安全、速度上限、共同域，以及两群是否在同一段终端窗口同时通过。不能把不同时间的保持窗口拼成系统成功。只有群级和系统级都通过，并且流程状态正常，才记 `deployment_success=true`。预检记录保持只读。
